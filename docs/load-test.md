# Нагрузочный тест

**Итог:** продакшен держит 10 RPS без ошибок с запасом в 5 раз — при 50 RPS ошибок нет, p95 — 361 мс.

- **Когда:** 14.10.2026, вечер (в это время в сервисе были живые пользователи).
- **Что:** продакшен https://семейныйдиспетчер.рф — VPS 2 vCPU / 4 ГБ, Docker: Caddy → FastAPI (uvicorn) → PostgreSQL.
- **Откуда:** обычный домашний компьютер через интернет, поэтому в задержки входит сеть: `/health` без работы с базой отвечает за ~200 мс — это и есть время сети туда-обратно.
- **Как:** [`backend/loadtest/loadtest.py`](../backend/loadtest/loadtest.py) — постоянный поток запросов с заданной частотой, 60 секунд на каждый уровень. Набор запросов повторяет открытие приложения: страница, сессия, семья, список дел, частые дела. Все запросы только читают — тест не создаёт дел и событий, не влияет на метрики и не тратит токены LLM. Авторизация — временная сессия тестового аккаунта команды, удалена после теста.

```bash
LOADTEST_TOKEN=<токен сессии> python backend/loadtest/loadtest.py https://xn--d1ababaqfaymzobir4fyc.xn--p1ai --rps 10 20 50 --seconds 60
```

## 100 RPS: найденная проблема и исправление

При 100 RPS с одной машины сервис перегрузился (2 ядра) и **не восстановился сам** после окончания нагрузки — 14.10 с 21:52 до 22:11 мск сайт не отвечал, помог перезапуск. Причина: запросы ждали соединение с базой (пул — 15), а запросы, уже державшие соединения, стояли в очереди за потоком для следующего шага; хвост из тысяч запросов разбирался со скоростью ~160 в минуту.

Исправление ([`backend/app/main.py`](../backend/app/main.py), `limit_api`): к базе одновременно идут не больше 15 запросов на процесс, пул соединений — с запасом вдвое, лишние запросы ждут на входе, после 10 с — быстрый ответ 503. Проверка на локальном стенде с тем же пулом при 500 RPS: без исправления сервис висел дольше 2,5 минуты после нагрузки, с исправлением — восстановился через 5 секунд, ошибок пула нет.

Повторно 100 RPS на продакшене не запускали, чтобы не мешать пользователям. Масштабирование при росте — больше процессов uvicorn и ядер; 2 ядер хватает с запасом для текущей нагрузки (пик — единицы RPS).

## Выводы

- Время работы сервера — разница с `/health`: 10–110 мс по p50. Самый тяжёлый запрос — список дел (`/api/v1/tasks`), +90 мс.
- Рост нагрузки с 10 до 50 RPS почти не меняет медиану; хвост p99 при 50 RPS — единичные запросы около 1,2 с.
- Узкое место при росте — не API, а LLM: разбор фразы в дело идёт через внешнюю модель (p50 1,2 с, p95 6,3 с по журналу обращений), Ожидание ограничено 8 секундами: при сбое или таймауте модели срабатывает разбор правилами, и дело всё равно создаётся. Разбор фразы в тест не включён, чтобы не тратить токены программы. Стоимость — [llm-cost.md](llm-cost.md).
